# 四类任务：人话阶段清单

内部 id：`bug_fix` · `new_feature` · `debug` · `small_change`。

其他类型（改已有功能、基础设施、文档、评审）MVP 不单独建模板，可临时映射到
`new_feature` 或 `small_change`。

---

## 修 Bug（`bug_fix`）

- [ ] 分类为修 Bug；加载 `bugfix-v1`
- [ ] 建 worktree + env
- [ ] 有复现步骤？没有就澄清；有就跳过或弱化 clarify
- [ ] Plan：列根因假设 + 最小改动面；注入项目/领域相关经验
- [ ] Develop：最小补丁
- [ ] Test：至少覆盖复现路径的回归
- [ ] Review → 开 PR → CI（可回环，受 `max_ci_loops` 限制）
- [ ] 经验：写「根因 + 易踩坑文件」到项目桶（必要时加领域桶）

**门禁要点：** 有复现或可造失败用例；PR 带回归。  
**澄清：** 描述不清才问；有稳定复现可跳过。

---

## 新功能（`new_feature`）

- [ ] 分类为新功能；加载 `feature-v1`
- [ ] 建 worktree + env
- [ ] **必须澄清**：验收标准写清，否则停在 clarify
- [ ] Plan：粗设计 + 风险 + 测试点；注入经验
- [ ] Develop → 验收相关测试 → Review → PR → CI
- [ ] 经验：写需求歧义点、模块边界

**门禁要点：** 验收标准可测；计划过门禁。  
**澄清：** 强制；缺验收就停。

---

## 排查/调试（`debug`）

- [ ] 分类为排查；加载 `debug-v1`
- [ ] 建 worktree + env（常要日志/复现脚本）
- [ ] 澄清「期望 vs 实际」（有完整日志可弱化）
- [ ] Plan：假设列表 + 探针计划
- [ ] Develop/诊断循环：打点 → 收集证据 → 修或出结论
- [ ] 交付二选一：修复 PR，或带证据的结论文档（可不改代码）
- [ ] 经验：写诊断路径、有效探针

**门禁要点：** 假设要有证据；交付「修了」或「结论」。  
**澄清：** 有日志可弱化；无则必须问清期望 vs 实际。

---

## 小改动（`small_change`）

- [ ] 分类为小改动；加载 `small-change-v1`
- [ ] 建 worktree（env 可轻量）
- [ ] 一般跳过 clarify；改动面大则升格为新功能/修 Bug
- [ ] 直接改 → 冒烟/相关测试 → Review → PR
- [ ] CI：通常短回环；超范围改动要打回重分类
- [ ] 经验：可选短条（配置/约定小坑）

**门禁要点：** 改动面小；别顺手套大改。  
**澄清：** 一般可跳过。
